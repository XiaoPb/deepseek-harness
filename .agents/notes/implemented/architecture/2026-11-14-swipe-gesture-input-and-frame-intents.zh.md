# Agent Note: 滑动手势的输入白名单、框架意图与不首尾回绕

Status: implemented

[English](2026-11-14-swipe-gesture-input-and-frame-intents.md) | 中文

## 问题

Web 客户端的触摸用户当时缺少两个最常用操作的手势。左右两栏只能通过按钮打开；宽度低于 768px 时，设置面板的分区导航变成只能点按的横向条。

有三个问题决定了本次工作的形态，每一个都完全可以有另一种答案：

1. **哪些指针算作滑动。** 触控板拖动、笔划和手指都以 pointer 事件到达；一个不加区分地接受它们的全页滑动监听器，会夺走依赖文本选择、桌面栏拖动和悬停交互的用户原本的交互。
2. **右栏展开状态归谁所有。** 该状态是 `ui-sidebar-right` 内部按会话划分的 store；框架是基础包，从不导入它。框架中的手势宿主无法读到该状态，而框架现有的 `ctx.layout` 报告是占用方发出的输出，不是发给它的命令。
3. **滑过第一个或最后一个分区时发生什么。** 分区数量随 profile 不同，因此无论选哪种行为，都必须为一个外壳并不拥有的列表定义规则。

## 决策

### 滑动输入规则是白名单

`isSwipePointer` 只接受主接触点的 `pointerType` 为 `touch` 与 `pen` 的情况。`pointerType` 是浏览器在系统层给出的设备分类，从不解析用户代理，因此规则精确且可测：鼠标与空分类保持原有交互，包括桌面端仍作为唯一路径的 8px 栏拖动手柄。

笔是直接指向的工具，因此与手指归为一类。代价是：在文本字段上水平拖动同样是笔或手指选择文本的方式，所以 `isFormControlTarget` 把起点落在表单控件上的手势留给该控件；起点落在带标记的滚动容器内、且沿拖动方向仍有滚动余量时，也留给滚动。

该规则位于 `ui-layout`，设置面板通过框架的 `./src/*` 子路径导入这一个纯模块，因为一个功能插件不得对另一个功能插件的 client 入口建立值依赖。

### 框架暴露右栏意图，而非状态

`ctx.layout` 新增 `openRightbarIntent()` 与 `closeRightbarIntent()`，以及由占用方调用的注册：在具体类 `LayoutController` 上的 `registerRightbarIntents({ open, close })`；它的 disposer 会恢复上一份注册，因此卸载后接口回到原有状态。没有注册时意图是空操作，因此没有右栏的 profile 无需特殊处理。

`ui-sidebar-right` 在自身的 apply 中注册这些意图，并以 `ISidebarRight.setExpanded(expanded)` 回应——这是与 `toggleExpanded()` 并列的单向命令。手势声明它已提交的方向；改用切换会在状态已经变化时把手势效果反转。意图作用于控制器认定为屏幕上的会话；没有屏幕会话、或该会话的 store 尚未由运行时铸出时，它什么也不做——意图不允许像一次点击那样大声失败。

框架不为滑动绘制抽屉动画：侧栏几何保持原有的端点过渡，意图改变的正是按钮已经在改变的那个 store。

### 条带呈现切换分区且不首尾回绕

设置面板自行从 `matchMedia('(max-width: 767px)')` 读取条带呈现，与已经把侧栏在同样宽度切换成条带的 CSS 相邻。

条带响应内容区上的水平滑动——面板宽度的四分之一，内容通过 CSS 变量跟随指针，拖动期间不进入 React state——以及导航上的方向键、Home 和 End。两者都停在第一个和最后一个分区。设置分区是有序的功能列表，滑过最后一个再回到第一个会丢失用户的位置感，因此该规则对所有 profile 统一。

同样的按键在桌面侧边轨道中保持无效，那里是一列纵向行，保留普通的 Tab 与点击行为；条带的每个单元格只保留一个 Tab 停靠点，焦点跟随选中项。

弹窗本身不禁用框架手势：框架目前没有手势宿主，也就没有可禁用的东西。将来框架加上手势宿主时，其启动条件必须拒绝在已打开对话框内按下的指针。

## 备选方案

- **以 `pointerType !== 'mouse'` 作为规则。** 否决：它会放行空分类——正是浏览器无法判断按下物、误判代价最大的情形。
- **以粗指针媒体查询作为规则。** 否决：粗指针机器同样可能由触控板或鼠标驱动；事件分类针对每次接触，而非整台设备。
- **在 `ctx.layout` 上为右栏暴露状态读取方法。** 否决：框架将读写另一个包的按会话状态，store 的归属方会出现两个写入者。
- **切换式意图。** 否决：它把已提交的方向变成与按下到抬起之间任何其他改动的竞争。
- **首尾回绕。** 否决：会丢失用户的位置感，并掩盖分区数量。
- **用分段标签原语实现条带。** 目前否决：设置导航是有图标座位与焦点恢复行为的 ledger 投影，迁移它比手势本身需要更大的改动。

## 影响

- 手势原语是带单元测试的纯函数；读取 DOM 的部分由各自的 spec 覆盖。
- 设置面板与将来的框架手势共用同一输入规则与同一进度曲线，两者不会漂移成不同阈值。
- 不报告指针分类的设备完全得不到手势。这是有意的：沉默好于侧栏在用户手下自己打开。
- `ui-layout` 的 `./client` 入口导出抽屉断点，`ui-sidebar-right` 因此读取框架自己的阈值，而不是第二份字面量。
